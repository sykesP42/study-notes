# C++ 虚函数与多态

> 本文档系统性地讲解 C++ 中**虚函数（virtual function）** 与**多态（polymorphism）** 的核心机制。虚函数是继承体系中最关键的特性，它使得父类可以定义通用的“算法骨架”，而将具体实现延迟到子类中完成。理解虚函数是掌握面向对象编程、设计模式和应用程序框架（如 MFC、Qt）的基础。

## 一、继承与虚函数

### 1.1 继承的内存视角

**继承的本质（从内存角度看）**：子类对象内部会完整包含一个父类的子对象（即父类的所有数据成员）。

```cpp

struct List_node_base {
    List_node_base* prev;
    List_node_base* next;
};
struct List_node : public List_node_base {
    int data;   // 子类自己增加的数据
};
```
**内存布局**：

```text

┌──────────────────────────────┐
│       List_node 对象         │
├──────────────────────────────┤
│   [父类部分]                  │
│   ├── prev   (4 字节)        │
│   └── next   (4 字节)        │
├──────────────────────────────┤
│   [子类自身部分]              │
│   └── data   (4 字节)        │
└──────────────────────────────┘
```
**关键理解**：子类对象 = 父类部分 + 子类自身部分。这个内存布局是理解继承下构造/析构顺序的基础。

### 1.2 函数的继承：继承的是“调用权”

在继承体系中，子类**继承的不是函数的内存**（函数代码只有一份），而是**函数的调用权**。子类可以调用父类的所有成员函数（取决于访问权限）。

但不同类型的成员函数，子类的“调用权”含义不同：

> 📖 **参考**：cppreference 虚函数 —— “虚函数是特殊的成员函数，在派生类中被重写时，通过基类指针或引用调用时会调用派生类的函数。”

### 1.3 三种成员函数

在继承体系中，根据是否允许子类重写（override），成员函数分为三种类型：

|类型|声明形式|特点|子类能否重写|
|---|---|---|---|
|**non-virtual 函数**|`void func()`|父类已有完整的默认实现，**不希望**子类重新定义|❌ 不应该重写|
|**virtual 函数**|`virtual void func()`|父类有默认实现，但**希望**子类可以重新定义（也可以不重写直接用父类的版本）|✅ 可以选择重写|
|**pure virtual 函数**|`virtual void func() = 0`|父类没有默认实现，**希望**子类**必须**重新定义|✅ **必须**重写|

**术语说明**：

- **override（覆写/重写）**：专指子类对**虚函数**的重新定义，不能用于非虚函数
    
- 子类重写虚函数时，建议使用 `override` 关键字（C++11 起），让编译器帮助检查是否正确重写了基类的虚函数
    

### 1.4 经典示例：Shape 类设计

```cpp

class Shape {
public:
    // non-virtual：获取对象ID，逻辑对所有子类都适用，不希望子类修改
    int objectID() const { return m_id; }
    
    // virtual：父类有默认错误提示，但允许子类提供更精细的错误信息
    virtual void error(const char* msg) {
        std::cout << "Shape error: " << msg << std::endl;
    }
    
    // pure virtual：父类无法定义如何绘制一个抽象的"形状"
    // 所有子类必须实现自己的绘制逻辑
    virtual void draw() const = 0;
    
private:
    int m_id;
};
class Circle : public Shape {
public:
    // 重写 virtual 函数（可选）
    void error(const char* msg) override {
        std::cout << "Circle error: " << msg << std::endl;
    }
    
    // 必须实现 pure virtual 函数
    void draw() const override {
        std::cout << "Drawing a Circle" << std::endl;
    }
};
class Rectangle : public Shape {
public:
    // 也可以选择不重写 error()，直接使用父类的默认版本
    
    // 必须实现 draw()
    void draw() const override {
        std::cout << "Drawing a Rectangle" << std::endl;
    }
};
```
**设计意图总结**：

| 函数类型         | 设计意图                   | 子类行为        |
| ------------ | ---------------------- | ----------- |
| non-virtual  | “父类说了算”                | 直接继承，不可改变   |
| virtual      | “父类有默认方案，但欢迎子类提供更好的方案” | 可以重写，也可以不重写 |
| pure virtual | “父类没有方案，子类必须自己决定”      | **必须**重写    |

> 📖 **参考**：cppreference 纯虚函数 —— “纯虚函数是未在基类中定义的虚函数，要求任何非抽象的派生类必须重写它。纯虚函数的声明使用 `= 0` 后缀。”

### 1.5 继承的真正威力：与虚函数搭配

继承本身只是“代码复用”的手段之一，其**真正的威力在于搭配虚函数使用**，实现**多态（Polymorphism）**——父类的接口可以调用子类的具体实现。

## 二、Template Method（模板方法）设计模式

### 2.1 问题场景：文件开启流程

任何程序开启文件都包含一系列固定步骤：

1. 弹出对话框，供用户选择文件
    
2. 用户输入或选择文件名称
    
3. 程序检查文件名是否合法
    
4. 到硬盘中查找该文件是否存在
    
5. 找到后，执行“打开”操作
    
6. **将文件内容读取出来** ⬅️ 这是唯一无法预先编写的步骤！
    

**核心问题**：上述步骤中，只有最后一步“读取内容”无法预先编写，因为不同软件（如简报、文书、试算表）读取的数据格式完全不同。

### 2.2 解法：Template Method 模式

**Template Method（模板方法）** 是一种经典的设计模式，用于解决 **“固定流程 + 可变步骤”** 的问题。

**核心思想**：

- 在父类中定义一个算法的**骨架（固定步骤）**
    
- 将其中某些步骤的实现**延迟（defer）** 到子类中完成
    
- 无法确定的步骤被设计为**虚函数**，由子类去覆写（override）
    

```cpp

// 父类：定义了算法的骨架
class CDocument {
public:
    // 这是一个 non-virtual 函数，定义了固定的算法骨架
    // 这就是 Template Method 本身
    void OnFileOpen() {
        std::cout << "1. 弹出对话框，让用户选择文件" << std::endl;
        std::cout << "2. 用户输入文件名" << std::endl;
        std::cout << "3. 检查文件名是否合法" << std::endl;
        std::cout << "4. 在硬盘中查找文件是否存在" << std::endl;
        std::cout << "5. 打开文件" << std::endl;
        
        // 关键：调用虚函数，将可变步骤延迟到子类
        Serialize();
        
        std::cout << "7. 关闭文件，完成操作" << std::endl;
    }
    
    // 虚函数：父类有默认实现（可能为空），但希望子类重写
    virtual void Serialize() {
        // 默认的空实现，或者提供一些通用逻辑
        std::cout << "(父类默认的 Serialize，什么也不做)" << std::endl;
    }
};
// 子类：实现具体的可变步骤
class CMyDoc : public CDocument {
public:
    // 重写虚函数，提供具体的文件读取逻辑
    void Serialize() override {
        std::cout << "6. 子类 CMyDoc 读取自己的文件格式" << std::endl;
        // 应用程序才知道自己的文件格式如何读取
    }
};
// 使用
int main() {
    CMyDoc myDoc;
    myDoc.OnFileOpen();   // 调用父类的 Template Method
    return 0;
}
```
### 2.3 执行流程与关键机制

**执行流程**：

1. 创建子类对象 `CMyDoc myDoc`
    
2. 通过子类对象调用父类的 `OnFileOpen()` 函数
    
3. 父类 `OnFileOpen()` 执行固定步骤
    
4. 执行到 `Serialize()` 时，由于该函数是虚函数，实际会调用**子类 `CMyDoc` 中覆写的 `Serialize()`** 版本
    
5. 子类 `Serialize()` 执行完毕后，返回父类 `OnFileOpen()` 继续执行剩余步骤
    

**关键机制：`this` 指针的传递**

```cpp

CMyDoc myDoc;
myDoc.OnFileOpen();   // 调用时，this 指向的是 myDoc（CMyDoc 类型）
```
当子类对象调用父类函数时，`this` 指针指向的是**子类对象本身**。父类函数内部通过 `this` 调用虚函数时，会根据 `this` 的实际类型（子类类型）调用到子类的实现版本。这就是多态的底层机制。

### 2.4 应用框架（Framework）

将 Template Method 模式大规模应用，就形成了**应用框架（Framework）**。

- **MFC（Microsoft Foundation Classes）** 就是一套预先写好的应用程序框架
    
- 框架开发者将通用的、固定的操作（如文件开启对话框、文件检查等）全部写好
    
- 只留下与具体业务逻辑相关的部分（如读取文件内容）作为**虚函数**，让使用者去实现
    
- 使用者只需要继承框架提供的类，并重写关键的虚函数
    

> **核心思想**：框架作者说：“我帮你把 80% 的工作都做好了，剩下 20% 你只需要重写我预留的几个虚函数就行。”

> 📖 **参考**：cppreference —— “Template Method 是一种行为设计模式，它在基类中定义算法的骨架，同时允许子类在不改变算法结构的情况下重新定义算法的某些步骤。”

## 三、继承 + 复合下的构造与析构顺序

### 3.1 问题场景

当一个类**同时使用继承和复合**时，构造和析构的顺序需要明确。

```cpp

class Component {
public:
    Component() { std::cout << "Component 构造" << std::endl; }
    ~Component() { std::cout << "Component 析构" << std::endl; }
};
class Base {
public:
    Base() { std::cout << "Base 构造" << std::endl; }
    ~Base() { std::cout << "Base 析构" << std::endl; }
private:
    Component comp;   // 父类内部复合了一个 Component 对象
};
class Derived : public Base {
public:
    Derived() { std::cout << "Derived 构造" << std::endl; }
    ~Derived() { std::cout << "Derived 析构" << std::endl; }
};
```
**内存布局**：

```text

┌──────────────────────────────┐
│       Derived 对象            │
├──────────────────────────────┤
│   [父类 Base 部分]            │
│   ┌────────────────────────┐ │
│   │ [Component 部分]        │ │
│   └────────────────────────┘ │
└──────────────────────────────┘
```
### 3.2 构造顺序

**规则：由内而外，先构造最内层的成员，再逐层向外。**

对于 `Derived d;`：

1. **最内层：`Component` 的构造函数**（因为它是 `Base` 中最先被构造的成员）
    
2. **`Base` 的构造函数**（父类部分）
    
3. **`Derived` 的构造函数**（子类自身部分）
    

**输出顺序**：

```text

Component 构造
Base 构造
Derived 构造
```
### 3.3 析构顺序

**规则：与构造顺序完全相反，由外而内。**

对于 `Derived d;`（离开作用域时）：

1. **`Derived` 的析构函数**（子类自身部分先销毁）
    
2. **`Base` 的析构函数**（父类部分）
    
3. **`Component` 的析构函数**（最内层最后销毁）
    

**输出顺序**：

```text

Derived 析构
Base 析构
Component 析构
```
### 3.4 核心原则

|阶段|顺序|记忆口诀|
|---|---|---|
|构造|**由内而外**|先造最里面的零件，再造外壳|
|析构|**由外而内**|先拆外壳，再拆里面的零件|

> 📖 **参考**：cppreference 构造函数 —— “成员的初始化顺序是按照类中声明的顺序进行的，基类总是在成员之前初始化。”析构函数 —— “析构函数体首先执行，然后按成员声明顺序的逆序调用成员的析构函数，最后调用基类的析构函数。”

## 四、委托 + 继承 —— Observer（观察者）模式

### 4.1 问题场景：一份数据，多个视图

在 PowerPoint 或 Word 中，可以打开**多个窗口查看同一份文档**：

- 数据只有一份（文档内容）
    
- 但多个视图（窗口）需要同步更新
    
- 核心需求：**当数据发生变化时，所有观察该数据的视图都必须自动更新**
    

### 4.2 解法：Observer 模式

**Observer（观察者）模式**使用 **委托（Delegation）+ 继承（Inheritance）** 的组合来解决这个问题：

```text

┌─────────────┐         ┌─────────────────┐
│   Subject   │────────▶│    Observer     │
│  （数据）   │  指针   │   （观察者）   │
│             │◀────────│   (抽象基类)    │
│  - m_views  │  容器   └────────┬────────┘
│  + attach() │         ┌────────┴────────┐
│  + notify() │         │                 │
│  + setData()│    ┌────▼────┐     ┌─────▼────┐
└─────────────┘    │ObserverA│     │ObserverB │
                   │(具体观察者)│     │(具体观察者)│
                   └─────────┘     └──────────┘
```
**各部分的职责**：

|角色|职责|实现方式|
|---|---|---|
|**Subject（数据/主题）**|持有数据，管理所有观察者，数据变化时通知所有观察者|通过**委托**持有 `Observer` 指针的容器|
|**Observer（观察者接口）**|定义观察者接收通知的统一接口|**抽象基类**，包含纯虚函数 `update()`|
|**具体 Observer**|实现自己的更新逻辑（如何刷新显示）|通过**继承**实现多态的观察者|

### 4.3 代码示例

```cpp

#include <iostream>
#include <vector>
#include <algorithm>
// ===== Observer: 抽象基类 =====
class Observer {
public:
    // 纯虚函数：所有观察者必须实现自己的更新逻辑
    virtual void update(int newData) = 0;
    virtual ~Observer() = default;
};
// ===== Subject: 数据源 =====
class Subject {
private:
    int m_data;
    std::vector<Observer*> m_views;   // Delegation: 持有观察者指针
    
public:
    void attach(Observer* obs) {
        m_views.push_back(obs);
    }
    
    void detach(Observer* obs) {
        auto it = std::find(m_views.begin(), m_views.end(), obs);
        if (it != m_views.end()) {
            m_views.erase(it);
        }
    }
    
    void setData(int newData) {
        m_data = newData;
        notifyAll();   // 数据变化时，自动通知所有观察者
    }
    
    void notifyAll() {
        for (Observer* obs : m_views) {
            obs->update(m_data);   // 每个观察者接收到通知后自行更新
        }
    }
};
// ===== 具体观察者 A =====
class ObserverA : public Observer {
public:
    void update(int newData) override {
        std::cout << "ObserverA 收到数据更新: " << newData << " (A 方式显示)" << std::endl;
    }
};
// ===== 具体观察者 B =====
class ObserverB : public Observer {
public:
    void update(int newData) override {
        std::cout << "ObserverB 收到数据更新: " << newData << " (B 方式显示)" << std::endl;
    }
};
// ===== 使用 =====
int main() {
    Subject subject;
    ObserverA a;
    ObserverB b;
    
    subject.attach(&a);
    subject.attach(&b);
    
    subject.setData(100);  // 数据变化，自动通知 a 和 b
    // 输出：
    // ObserverA 收到数据更新: 100 (A 方式显示)
    // ObserverB 收到数据更新: 100 (B 方式显示)
    
    return 0;
}
```
### 4.4 设计模式的意义

Observer 模式是 **23 个设计模式**中的一个经典例子，用于解决 **数据与视图同步更新** 的问题。

**为什么 Delegation + Inheritance 组合如此强大？**

- **Delegation**（委托）：Subject 通过指针持有 Observer，**不关心具体是哪种观察者**
    
- **Inheritance**（继承）：不同的观察者继承自同一个 Observer 基类，**实现了多态**
    
- 组合效果：Subject 可以管理**任意数量、任意类型**的观察者，而无需知道它们的细节
    

> 📖 **参考**：cppreference —— “观察者模式是一种行为设计模式，它允许你定义一种订阅机制，在对象事件发生时通知多个观察该对象的其他对象。”

## 五、知识小结

### 5.1 核心概念速查表

|知识点|核心内容|关键要点|
|---|---|---|
|**虚函数**|在成员函数前加 `virtual` 关键字|子类可以 override；通过基类指针/引用调用时会调用子类版本|
|**纯虚函数**|`virtual void func() = 0`|子类**必须**重写；使类变为抽象类|
|**non-virtual 函数**|普通成员函数|不希望子类重写；逻辑对所有子类通用|
|**三种函数分类**|non-virtual、virtual、pure virtual|三种函数的设计意图不同，对应“父类说了算”“父类有默认方案”“父类没有方案”三种场景|
|**override 关键字**|C++11 起，在重写的虚函数后加 `override`|让编译器检查是否正确重写了基类的虚函数|
|**Template Method**|父类定义算法骨架，将可变步骤设为虚函数|经典设计模式；MFC 等框架大量使用|
|**继承+复合构造顺序**|有父类和 Component 时|构造：Component → Base → Derived；析构相反|
|**Observer 模式**|Subject 通过 Delegation 持有 Observer 列表|Observer 通过 Inheritance 实现多态；解决数据与视图同步问题|
|**框架（Framework）**|预先写好通用流程，虚函数留给子类实现|如 MFC、Qt 等|

### 5.2 三种成员函数对比

|对比项|non-virtual|virtual|pure virtual|
|---|---|---|---|
|声明方式|`void func()`|`virtual void func()`|`virtual void func() = 0`|
|父类是否有实现|✅ 有完整实现|✅ 有默认实现|❌ 通常没有实现|
|子类能否重写|❌ 不应该重写|✅ 可以选择重写|✅ **必须**重写|
|子类能否直接使用父类版本|✅ 可以|✅ 可以|❌ 不能（没有实现）|
|设计意图|“父类说了算”|“欢迎子类提供更好的方案”|“子类必须自己决定”|
|类是否可实例化|不影响|不影响|有纯虚函数的类是**抽象类**，不可实例化|

### 5.3 构造/析构顺序总结

|场景|构造顺序|析构顺序|
|---|---|---|
|**仅继承**|Base → Derived|Derived → Base|
|**仅复合**|Component → Container|Container → Component|
|**继承 + 复合**|Component → Base → Derived|Derived → Base → Component|

**记忆口诀**：

- 构造：**由内而外**，先造零件再造外壳
    
- 析构：**由外而内**，先拆外壳再拆零件
