# C++ 委托相关设计：Composite 与 Prototype 模式

> 本文档是侯捷《C++面向对象高级开发》课程的最后一讲，在前面学习了三种类关系（复合、委托、继承）以及虚函数与多态的基础上，进一步讲解**如何将这些基础机制组合使用来解决更复杂的设计问题**。核心内容涵盖 **Composite（组合）模式** 和 **Prototype（原型）模式**，这是理解“如何用三大武器解决现实问题”的关键一步。

## 一、回顾：三种基本关系及其典型模式

### 1.1 复合（Composition）+ Adapter（适配器）模式

**复合**（Composition）表示 **“has-a”**（有一个）关系，即一个类包含另一个类的对象作为成员。

**Adapter（适配器）模式**：通过复合关系，将一个类的接口转换成客户希望的另一个接口。

```cpp

template <class T, class Container = deque<T>>
class queue {
public:
    void push(const T& x) { c.push_back(x); }   // 适配：改名
    void pop() { c.pop_front(); }                // 适配：改名
    T& front() { return c.front(); }
    bool empty() const { return c.empty(); }
private:
    Container c;   // 复合：queue 包含一个 deque 对象
};
```
**关键理解**：`queue` 本身不实现任何功能，只是将接口“改装”后委托给 `deque` 完成。这就是 **Adapter（适配器）模式** 的典型实现——**功能不变，接口改名**。

> 📖 **参考**：cppreference `std::queue` —— “`std::queue` 是一个容器适配器，为 FIFO 数据结构提供功能。”

### 1.2 委托（Delegation）+ Handle/Body（pimpl）模式

**委托**（Delegation）也称为 **“Composition by reference”**，一个类通过指针引用另一个类，将任务委托给它执行。

**Handle/Body 模式（pimpl）**：接口与实现分离，修改 Body 不影响 Handle 的接口。

```cpp

// String.h（对外接口）
class String {
public:
    String();
    String(const char* s);
    String(const String& s);
    String& operator=(const String& s);
    ~String();
    // ... 其他接口
private:
    StringRep* rep;   // 委托：指向真正的实现
};
// StringRep.h（内部实现，可以自由修改）
class StringRep {
    // 真正的数据与实现
    friend class String;
    StringRep(const char* s);
    void increment() { ++count; }
    void decrement() { if (--count == 0) delete this; }
private:
    int count;        // 引用计数
    char* data;
};
```
**优点**：实现了“编译防火墙”——修改 `StringRep` 不影响 `String` 的接口，客户端无需重新编译。

### 1.3 继承（Inheritance）+ Template Method（模板方法）模式

**继承**表示 **“is-a”**（是一种）关系。

**Template Method 模式**：父类定义算法骨架，将某些步骤延迟到子类中实现。

```cpp

class CDocument {
public:
    void OnFileOpen() {          // Template Method
        // ... 固定步骤 ...
        Serialize();             // 调用虚函数，延迟到子类
        // ... 后续步骤 ...
    }
    virtual void Serialize() { } // 子类重写此函数
};
class CMyDoc : public CDocument {
    void Serialize() override {
        // 子类实现具体的文件读取逻辑
    }
};
```
**核心思想**：父类控制流程，子类提供具体行为——“好莱坞原则”（Don‘t call us, we’ll call you）。

## 二、Composite（组合）模式

### 2.1 问题场景：文件系统 / 窗口系统

在设计文件系统时，会遇到一个典型的**嵌套结构**问题：

```text

文件系统
├── 文件A.txt          ← 个体（Primitive）
├── 文件夹1            ← 容器（Composite）
│   ├── 文件B.txt      ← 个体
│   └── 文件夹2        ← 容器（嵌套！）
│       └── 文件C.txt
└── 文件D.jpg          ← 个体
```
**特征**：

- **容器（Composite）** 里可以放**个体（Primitive）**
    
- **容器（Composite）** 里也可以放**其他容器（Composite）**
    
- 这种嵌套可以无限深入
    

同样的模式也出现在窗口系统中：大窗口里可以有小窗口，小窗口里还可以有更小的窗口。

### 2.2 核心问题：容器如何同时容纳个体与其他容器？

**直接问题**：`Composite` 容器需要既能存放 `Primitive`，又能存放 `Composite`。

**解决方案**：为 `Primitive` 和 `Composite` 设计一个**共同的父类 `Component`**。

```text

        ┌─────────────┐
        │  Component  │  ← 共同的抽象父类
        │  (抽象类)   │
        └──────┬──────┘
               │
       ┌───────┴───────┐
       │               │
┌──────▼──────┐ ┌──────▼──────┐
│  Primitive  │ │  Composite  │
│  (叶子节点) │ │  (容器节点) │
└─────────────┘ └──────┬──────┘
                       │ 包含
                  ┌────▼────┐
                  │ vector< │
                  │Component│
                  │   *>    │  ← 存放父类指针！
                  └─────────┘
```

**关键设计**：

- **继承关系**：`Primitive` 和 `Composite` 都继承自 `Component`（**“is-a”关系**）
    
- **容器声明**：`Composite` 内部的容器存放的是**指向父类 `Component` 的指针**
    

**为什么必须用指针？**

C++ 容器要求存放的元素大小一致。不同的子类对象（`Primitive` 和 `Composite`）大小可能不同，不能直接存放对象。而**指针的大小是固定的**（32位平台4字节，64位平台8字节），因此存放指针可以解决此问题。

```cpp

class Component {
public:
    virtual void draw() = 0;
    // add() 函数不能是纯虚函数！
    virtual void add(Component* c) { }
    virtual ~Component() = default;
};
class Primitive : public Component {
public:
    void draw() override {
        std::cout << "Drawing a primitive" << std::endl;
    }
    // 继承 Component 中 add() 的空实现，什么都不做
    // 文件不能添加子元素，符合现实逻辑
};
class Composite : public Component {
private:
    std::vector<Component*> children;   // 存放父类指针
public:
    void draw() override {
        for (Component* c : children) {
            c->draw();   // 多态调用，每个子元素自己决定如何绘制
        }
    }
    void add(Component* c) override {
        children.push_back(c);   // 可以添加任何 Component 的子类
    }
};
```

### 2.3 为什么 `add()` 不能是纯虚函数？

这是一个容易出错的关键设计点。

**错误的做法**（将 `add()` 设为纯虚函数）：

```cpp

class Component {
public:
    virtual void add(Component* c) = 0;   // ❌ 错误！
};
```
如果 `add()` 是纯虚函数，那么 `Primitive`（叶子节点，如文件）**必须强制实现它**。但在现实中，文件无法添加子元素，强制实现 `add()` 要么是空实现（违背纯虚函数的语义），要么抛出异常（让调用者困惑）。

**正确的做法**（将 `add()` 设为普通虚函数，提供空实现）：

```cpp

class Component {
public:
    virtual void add(Component* c) { }   // ✅ 正确的做法
};
```
- **`Primitive`**：直接继承空实现，调用 `add()` 什么也不做，符合“文件不能加东西”的现实逻辑
    
- **`Composite`**：重写 `add()`，将传入的指针存入容器
    

**核心原则**：不是所有子类都需要所有功能。让不必要的子类继承一个“什么都不做”的默认实现，比强制它们实现一个无法合理实现的功能更合理。

> 📖 **参考**：cppreference —— “组合模式是一种结构型设计模式，它允许你将对象组合成树形结构来表现‘部分-整体’的层次结构。组合模式使得客户端可以统一对待单个对象和组合对象。”

### 2.4 Composite 模式知识点总结

|设计要点|说明|
|---|---|
|**共同父类**|`Primitive` 和 `Composite` 继承自同一个 `Component` 基类|
|**容器存放指针**|因为子类对象大小不同，必须存放 `Component*`|
|**`add()` 是普通虚函数**|提供空实现，`Primitive` 无需重写，`Composite` 重写以实现添加|
|**`draw()` 是纯虚函数**|每个具体类必须实现自己的绘制逻辑|

## 三、Prototype（原型）模式

### 3.1 问题场景：框架如何创建“未来”的子类对象？

**场景**：设计一个框架（Framework），框架的代码在编写时，其子类（如 `LandSatImage`、`SpotImage`）**尚未被客户定义，类名未知**。

```cpp

// 框架代码（框架作者编写，此时子类还不存在）
class Image {
    static Image* findAndClone(ImageType type) {
        // 问题：无法直接 new 子类，因为类名未知！
        // 不能写：return new LandSatImage(); 
    }
};
// 用户代码（未来才由客户编写）
class LandSatImage : public Image {
    // ...
};
```
**核心矛盾**：在 C++ 中，`new` 关键字后面**必须跟一个具体的类名**。框架代码无法在编译时知道未来的类名，因此无法直接创建子类对象。

### 3.2 解法思路：Prototype（原型）模式

**核心思想**：让未来的子类在定义时，先创建一个自己的实例作为**“原型（Prototype）”**，并注册到框架中。框架通过**克隆（clone）** 这些原型来创建新对象。

**不要问我怎么创建对象，给我一个原型，我复制它。**

### 3.3 完整实现

#### 父类 `Image`：框架端代码

```cpp

enum ImageType { LSAT, SPOT };
class Image {
public:
    // 纯虚函数：子类必须实现
    virtual void draw() = 0;
    virtual ImageType returnType() const = 0;
    virtual Image* clone() const = 0;   // 关键：克隆接口
    
    // 静态函数：框架提供给外界的接口
    static Image* findAndClone(ImageType type) {
        for (int i = 0; i < nextSlot; ++i) {
            if (prototypes[i]->returnType() == type) {
                return prototypes[i]->clone();   // 克隆一份副本
            }
        }
        return nullptr;
    }
    
protected:
    static void addPrototype(Image* image) {
        if (nextSlot < 10) {
            prototypes[nextSlot++] = image;
        }
    }
    
private:
    // 静态数组：存放所有已注册的原型
    static Image* prototypes[10];
    static int nextSlot;
};
// 静态数据成员必须在类外定义（分配内存）
Image* Image::prototypes[10];
int Image::nextSlot = 0;
```
#### 子类 `LandSatImage`：用户端代码

```cpp

class LandSatImage : public Image {
public:
    // 实现纯虚函数
    ImageType returnType() const override { return LSAT; }
    void draw() const override {
        std::cout << "LandSatImage::draw " << id << std::endl;
    }
    
    // 克隆函数：创建一份副本
    Image* clone() const override {
        return new LandSatImage(1);   // 调用带参数的构造函数
    }
    
private:
    int id;
    static int nextId;
    
    // 【关键】默认构造函数：只用于创建原型对象
    LandSatImage() {
        addPrototype(this);   // 注册自身到父类的原型数组
        id = ++nextId;
    }
    
    // 【关键】带参数的构造函数：只用于克隆
    LandSatImage(int dummy) {
        id = ++nextId;        // 只初始化 id，不再注册
    }
    
    // 静态原型对象：程序启动时自动创建，触发注册
    static LandSatImage landSatImage;
};
// 定义静态成员
int LandSatImage::nextId = 0;
LandSatImage LandSatImage::landSatImage;   // 静态原型的定义
```
**注意**：在 C++ 中，类的**静态数据成员**（`static` 成员）必须在类外进行**定义（definition）**，而非仅仅声明。`static LandSatImage landSatImage;` 只是声明，`LandSatImage LandSatImage::landSatImage;` 才是定义——它为这个静态对象分配了真正的内存。

### 3.4 两个构造函数的巧妙分工

|构造函数|用途|调用时机|操作|
|---|---|---|---|
|**默认构造函数（private）**|创建原型对象|程序启动时（静态对象初始化）|调用 `addPrototype(this)`，注册到父类的原型数组|
|**带参构造函数（protected）**|克隆新对象|调用 `clone()` 时|只初始化对象，**不**调用 `addPrototype()`，避免重复注册|

**为什么需要两个构造函数？**

- 如果只有一个构造函数，那么无论是创建原型还是克隆对象，都会调用 `addPrototype()`，导致原型被重复注册，或者新对象被错误地当作原型。
    
- 通过增加一个无用的 `int dummy` 参数来区分两种场景，是一个经典的设计技巧。
    

**访问权限**：两个构造函数都设置为 `private` 或 `protected`，防止外部直接创建对象，强制通过原型模式创建。

### 3.5 原型模式的执行流程

```text

程序启动（main 之前）
│
├── 静态对象 LandSatImage::landSatImage 被创建
│   └── 调用 LandSatImage()（默认构造函数）
│       └── addPrototype(this) → 将原型注册到 Image::prototypes[]
│
├── 静态对象 SpotImage::spotImage 同理注册
│
程序运行
│
客户端调用 Image::findAndClone(LSAT)
│
├── 遍历 prototypes[]，找到 returnType() == LSAT 的原型
│   └── 调用该原型的 clone()
│       └── new LandSatImage(1)（带参构造函数）
│           └── 返回一个全新的 LandSatImage 对象
```
### 3.6 原型的负担与合理性

**子类的额外负担**：每个使用 Prototype 模式的子类必须承担以下工作：

1. 声明一个**静态的自身对象**作为原型
    
2. 编写一个**私有的默认构造函数**（用于注册原型）
    
3. 编写一个**带参的构造函数**（用于克隆）
    
4. 实现 `clone()` 函数
    
5. 在类外**定义静态对象**（分配内存）
    

**合理性**：世界上没有白吃的午餐。要使用框架提供的便利，就必须遵循框架的约定，付出相应的编码代价。这是**与框架协作的必然要求**。

### 3.7 Prototype 模式知识点总结

|设计要点|说明|
|---|---|
|**静态原型对象**|每个子类创建一个静态自身对象，程序启动时自动注册|
|**私有构造函数（默认）**|用于创建原型，调用 `addPrototype()` 完成注册|
|**另一个构造函数（带参）**|用于克隆，只初始化对象，不注册|
|**`clone()` 纯虚函数**|要求子类实现自我复制的方法|
|**静态数据成员必须在类外定义**|类内只是声明，类外定义才真正分配内存|
|**框架不直接 `new`**|框架通过 `findAndClone()` 查找匹配的原型并克隆|

## 四、知识小结

### 4.1 本章设计模式对比

|模式|使用的类关系|解决的问题|关键技巧|
|---|---|---|---|
|**Adapter**|复合（Composition）|接口转换|功能不变，接口改名；如 `queue` 适配 `deque`|
|**Handle/Body (pimpl)**|委托（Delegation）|接口与实现分离|通过指针持有实现，编译防火墙|
|**Template Method**|继承（Inheritance）|固定流程 + 可变步骤|父类定义骨架，子类重写虚函数|
|**Observer**|委托 + 继承|一对多通知|Subject 通过指针持有 Observer 列表|
|**Composite**|继承 + 委托|树形结构、部分-整体|共同父类 + 容器存放父类指针|
|**Prototype**|继承 + 静态成员|创建未来才出现的子类对象|静态原型 + `clone()`|

### 4.2 核心概念速查表

|知识点|核心内容|关键要点|
|---|---|---|
|**Composite 模式**|用树形结构表示“部分-整体”层次，统一处理单个对象与组合对象|容器中必须存放指针（因对象大小不同）；`add()` 函数不能设为纯虚函数（叶子节点无需实现）|
|**Prototype 模式**|通过克隆原型对象创建新实例，解决未来类名未知的问题|静态原型对象 + 私有构造函数 + `clone()` 函数；需两个构造函数区分“创建原型”与“克隆副本”|
|**静态数据成员定义**|类中声明，类外定义|`static Type Class::member = value;` 才是定义，分配内存|
|**框架设计**|框架预先写好通用流程，子类通过注册原型参与|静态对象在 `main` 之前构造，完成注册|
|**设计模式的代价**|使用模式需要遵循约定，付出额外编码代价|没有“白吃的午餐”，但代价换取灵活性和可扩展性|

### 4.3 设计模式学习心法

1. **三大武器是基础**：继承、复合、委托是解决一切类关系问题的三把“大刀”
    
2. **从问题出发**：先理解“为什么要这样设计”，而不是死记模式名称
    
3. **模式是经验总结**：23 个设计模式是前人解决特定问题的经典方案，不是教条
    
4. **大量实践**：理解设计模式的最佳方式是写代码、改代码、调试代码
