# C++ 类与类之间的关系：复合、委托与继承

> 本文档系统性地讲解 C++ 中类与类之间的三种核心关系：**复合（Composition）**、**委托（Delegation）** 和 **继承（Inheritance）**。这是从“基于对象”（单一 class 设计）迈向“面向对象”（多个 class 协作设计）的关键一步。理解这三种关系及其构造/析构顺序、内存布局，是掌握面向对象编程（OOP）和面向对象设计（OOD）的基础。

## 一、类与类之间的三大关系

在面向对象程序设计中，类与类之间主要存在三种关系：

|关系|英文|中文含义|图示符号（UML）|典型描述|
|---|---|---|---|---|
|**复合**|Composition|“has-a”（有一个）|实心菱形|一个类包含另一个类的对象|
|**委托**|Delegation|“has-a”（通过指针）|空心菱形|一个类拥有指向另一个类的指针|
|**继承**|Inheritance|“is-a”（是一种）|空心三角形|子类是父类的一种特殊类型|

> 📖 **参考**：cppreference 类 —— “类（Class）是用户定义的类型，包含数据成员和成员函数。类可以继承自其他类，也可以作为其他类的成员。”

## 二、复合（Composition）

### 2.1 定义与基本概念

**复合（Composition）** 指一个类内部包含另一个类的对象作为成员，即 **“has-a”（有一个）** 关系。这是面向对象中最基本的关系，在 C 语言的结构体中就已存在（结构体嵌套）。


```cpp

class A {
    // ...
};
class B {
private:
    A a;   // B 包含了一个 A 对象 —— 复合关系
};
```
在 UML 类图中，拥有者一端用**实心菱形（黑色菱形）** 表示。

### 2.2 典型示例：标准库 `queue` 容器适配器

C++ 标准库中的 `queue`（队列）是一个经典的复合关系示例：

```cpp

template <class T, class Container = deque<T>>
class queue {
public:
    // 所有操作都委托给内部的 deque 对象
    void push(const T& x) { c.push_back(x); }   // 入队 -> 尾部插入
    void pop() { c.pop_front(); }               // 出队 -> 头部删除
    T& front() { return c.front(); }
    T& back() { return c.back(); }
    bool empty() const { return c.empty(); }
    size_type size() const { return c.size(); }
    // ...
private:
    Container c;   // 复合关系：queue 内部包含一个 Container 对象（默认为 deque）
};
```
**设计模式视角：Adapter（适配器）模式**

`queue` 本质上是对 `deque`（双端队列）的“改装”：

- **功能裁剪**：`deque` 支持两端进出，功能强大；`queue` 只开放了 6 个接口，实现先进先出（FIFO）
    
- **接口重命名**：将 `deque.pop_front()` 改名为 `pop()`，`deque.push_back()` 改名为 `push()`
    
- **类比**：就像电压适配器，将已有的东西（`deque`）改造成客户需要的接口（`queue`）
    

**核心特点**：`queue` 本身不实现任何功能，所有操作都“委托”给内部的 `deque` 对象完成。这是复合关系的一种特例——**“完全借用已有功能”**。

> 📖 **参考**：cppreference `std::queue` —— “`std::queue` 是一个容器适配器，为 FIFO（先进先出）数据结构提供功能。其底层容器可以是任何满足 `SequenceContainer` 要求的容器。”

### 2.3 复合关系的内存布局

在复合关系中，外部容器对象的大小等于其内部所有组件对象大小的**总和**。

**`queue` 的内存分析**（以 32 位平台为例）：

```text

queue (适配器)
    └── deque (底层容器)  ← queue 的大小 = deque 的大小
            ├── start (迭代器) → 4 个指针 × 4 字节 = 16 字节
            ├── finish (迭代器) → 4 个指针 × 4 字节 = 16 字节
            ├── map (指针的指针) → 4 字节
            └── map_size (无符号整数) → 4 字节
            总计：16 + 16 + 4 + 4 = 40 字节
```
**迭代器内部结构**：每个迭代器包含 4 个指针（cur, first, last, node），每个指针 4 字节，共 16 字节。

> 📖 **参考**：cppreference `std::deque` —— “`std::deque`（双端队列）是一个序列容器，允许在两端进行常数时间的插入和删除操作。典型的实现使用一系列独立分配的固定大小数组，需要额外的间接访问。”

### 2.4 复合关系下的构造与析构顺序

这是复合关系中最容易出错的地方，必须牢记：

#### 构造顺序：**由内而外**

1. **先调用内部组件（Component）的默认构造函数**
    
2. **再执行外部容器（Container）自身的构造函数体**
    

```cpp

class Container {
public:
    Container() : component() {   // 初始化列表中，编译器自动插入对 component 默认构造的调用
        // 外部容器的构造体：此时内部组件已经构造完毕
    }
private:
    Component component;   // 内部组件
};
```
**实现机制**：编译器会自动在容器构造函数的**初始化列表**中添加对组件默认构造函数的调用。如果不想调用默认构造函数，开发者必须在初始化列表中显式指定调用哪个构造函数。

**为什么？** 内部组件是外部容器存在的基础。如果基础没有打好（先构造外壳），外壳就没有可以依托的对象。

#### 析构顺序：**由外而内**

1. **先执行外部容器（Container）自身的析构函数体**
    
2. **再调用内部组件（Component）的析构函数**
    

```cpp

class Container {
public:
    ~Container() {
        // 外部容器的析构体：此时内部组件还存在，可以安全使用
    }   // 编译器在这里自动插入 component.~Component()
private:
    Component component;
};
```
**为什么？** 外部容器是内部组件的“保护壳”。如果先析构内部组件（剥掉基础），外部容器可能会因为失去依赖而“塌陷”（访问已销毁的对象），导致程序崩溃。

#### 核心原则（一句话记忆）

|阶段|顺序|口诀|
|---|---|---|
|构造|由内而外|**先打好地基，再盖房子**|
|析构|由外而内|**先拆房子，再拆地基**|

> 📖 **参考**：cppreference 构造函数 —— “非委托构造函数在类成员的初始化列表完成后，执行函数体。成员的初始化顺序是按照类中声明的顺序进行的。”析构函数 —— “析构函数体首先执行，然后按成员声明顺序的逆序调用成员的析构函数，最后调用基类的析构函数。”

## 三、委托（Delegation）

### 3.1 定义与基本概念

**委托（Delegation）** 指两个类之间通过**指针**相连的关系。一个类（Handle）拥有一个指向另一个类（Body）的指针，在需要时将任务“委托”给指针指向的对象来执行。

这种关系也被称为 **“Composition by Reference”**（通过引用的复合），UML 中用**空心菱形（白色菱形）** 表示。

```cpp

class Body {
    // 真正的实现
};
class Handle {
private:
    Body* p_body;   // 通过指针指向 Body 对象
public:
    void doSomething() {
        p_body->doSomething();   // 将任务委托给 Body 执行
    }
};
```
### 3.2 与复合（Composition）的关键区别

|对比项|复合（Composition）|委托（Delegation）|
|---|---|---|
|关联方式|直接包含**对象**|包含**指针**|
|生命周期|**同步**：外部对象创建时内部对象也创建，销毁时也一起销毁|**不同步**：外部对象可以先创建，内部对象在需要时才创建|
|内存位置|内部对象直接嵌入外部对象|内部对象独立存在于堆上|
|灵活性|较低，内部类型固定|较高，指针可以切换指向不同的实现|

### 3.3 经典应用：Handle/Body 模式（pimpl）

`Handle/Body` 模式（也称为 **pimpl**，即 Pointer to Implementation）是委托关系的典型应用：

```text

┌─────────────┐         ┌─────────────────┐
│   Handle    │────────▶│      Body       │
│（对外接口） │  指针   │  （真正实现）   │
└─────────────┘         └─────────────────┘
```
**优点**：

1. **编译防火墙**：修改 Body 的实现不影响 Handle 的接口，客户端（使用 Handle 的代码）无需重新编译
    
2. **接口稳定**：对外暴露的 Handle 接口保持不变，内部实现可以自由变化
    
3. **实现切换**：指针可以指向不同的 Body 实现类，方便切换底层实现
    

### 3.4 引用计数（Reference Counting）—— 共享数据

委托关系的一个经典应用场景是**引用计数**，多个对象共享同一份数据，通过计数管理共享者的数量。

```text

┌─────────┐
│ String  │──┐
└─────────┘  │    ┌─────────────────┐
┌─────────┐  ├───▶│   StringRep     │
│ String  │──┘    │   count = 3     │
└─────────┘       │   data = "hello"│
┌─────────┐       └─────────────────┘
│ String  │──┘
└─────────┘
```
**工作流程**：

1. 三个 `String` 对象（如 `s1, s2, s3`）都指向同一个 `StringRep` 对象
    
2. `StringRep` 内部有一个 `count` 整数，记录有多少个 `String` 共享这份数据（count = 3）
    
3. 当一个新的 `String` 共享这份数据时，`count++`
    
4. 当一个 `String` 不再引用这份数据时，`count--`
    
5. 当 `count` 变为 0 时，自动释放 `StringRep` 对象
    

**写时复制（Copy on Write）**：

当其中一个共享者（如 `s1`）要修改内容时，不能影响其他共享者（`s2, s3`）：

1. 系统检测到 `count > 1`，说明还有其他对象在共享这份数据
    
2. 为发起修改的对象 `s1` 复制一份新的数据副本
    
3. `s1` 在副本上执行修改，指向新的 `StringRep` 对象
    
4. 原共享数据的 `count--`，由剩余未修改的对象继续共享
    

> 📖 **参考**：cppreference `std::shared_ptr` —— “`std::shared_ptr` 是一个智能指针，通过指针维护对象的共享所有权。多个 `shared_ptr` 对象可以拥有同一个对象，引用计数会在最后一个 `shared_ptr` 被销毁时释放对象。”

## 四、继承（Inheritance）

### 4.1 定义与基本概念

**继承（Inheritance）** 表示 **“is-a”（是一种）** 关系。例如：`List_node` 是一种 `List_node_base`，人类是一种哺乳类，哺乳类是一种动物。

```cpp

// 基类（父类）
struct List_node_base {
    List_node_base* prev;
    List_node_base* next;
};
// 派生类（子类）：public 继承
struct List_node : public List_node_base {
    int data;   // 额外的数据
};
```
**语法**：在子类名称后加 `: public 父类名称`。

**继承方式**：C++ 提供三种继承方式（`public`、`private`、`protected`），其中 **`public` 继承**最重要，用于表达 is-a 的逻辑关系。其他语言（如 Java）只有 `public` 继承。

> 📖 **参考**：cppreference 继承 —— “类可以从另一个类派生，其派生类的对象包含基类的子对象。`public` 继承建立了 is-a 关系。”

### 4.2 继承的内存视角

子类对象内部**包含父类的所有数据成员**（如同继承父亲的财产）：

```text

┌─────────────────────────┐
│   List_node 对象        │
├─────────────────────────┤
│   [父类部分]            │
│   List_node_base 数据   │  ← 继承自父类
│   ├── prev              │
│   └── next              │
├─────────────────────────┤
│   [子类自身部分]        │
│   data                  │  ← 子类自己增加的成员
└─────────────────────────┘
```
**子类对象的大小** = 父类数据部分 + 子类自身数据部分。

**继承的主要价值**：并非单纯为了复用数据，而是与**虚函数（virtual function）** 搭配使用，实现**多态（Polymorphism）**。

### 4.3 继承下的构造与析构顺序

与复合关系**完全一致**：

#### 构造顺序：**由内而外**

1. **先调用父类的构造函数**
    
2. **再执行子类自身的构造函数体**
    

```cpp

class Derived : public Base {
public:
    Derived(...) : Base(...) {   // 编译器在初始化列表中插入对父类构造函数的调用
        // 子类构造体：此时父类部分已经构造完毕
    }
};
```
#### 析构顺序：**由外而内**

1. **先执行子类自身的析构函数体**
    
2. **再调用父类的析构函数**
    

```cpp

class Derived : public Base {
public:
    ~Derived() {
        // 子类析构体：此时父类部分还存在，可以安全使用
    }   // 编译器在这里自动插入对父类析构函数的调用
};
```
#### ⚠️ 关键规则：父类的析构函数必须声明为 `virtual`

```cpp

class Base {
public:
    virtual ~Base() { }   // 必须声明为 virtual！
};
```
**为什么？**

- 当使用**基类指针**指向**派生类对象**，并通过 `delete` 删除该指针时，必须调用派生类的析构函数，实现“由外而内”的析构顺序
    
- 如果基类的析构函数不是 `virtual`，`delete base_ptr` 只会调用基类的析构函数，派生类的析构函数不会被调用，导致**未定义行为**（派生类部分无法正确析构）
    

```cpp

Base* p = new Derived();
delete p;   // 如果 Base 的析构函数不是 virtual，只会调用 Base::~Base()
```
**编程习惯**：只要一个类被设计为基类（或将来可能成为基类），就应将其析构函数设为 `virtual`。

> 📖 **参考**：cppreference 虚析构函数 —— “基类的析构函数应该是虚函数，以便在 `delete` 基类指针时正确调用派生类的析构函数。如果基类的析构函数不是虚函数，通过基类指针删除派生类对象的行为是未定义的。”

### 4.4 继承与复合的构造/析构顺序对比

|对比项|复合（Composition）|继承（Inheritance）|
|---|---|---|
|构造顺序|先构造内部组件，再构造外部容器|先构造父类部分，再构造子类部分|
|析构顺序|先析构外部容器，再析构内部组件|先析构子类部分，再析构父类部分|
|核心口诀|先内后外，先外后内|先父后子，先子后父|

## 五、虚函数（Virtual Functions）

### 5.1 三种类型的成员函数

在继承体系中，根据是否允许子类重写（override），成员函数分为三种：

|类型|声明方式|特点|子类能否重写|
|---|---|---|---|
|**non-virtual 函数**|普通函数|不希望子类重新定义|❌ 不能（或说不应该）|
|**virtual 函数**|`virtual void func()`|希望子类重新定义，且父类已有默认实现|✅ 可以重写，也可以不重写|
|**pure virtual 函数**|`virtual void func() = 0`|希望子类必须重新定义，父类没有默认实现|✅ **必须**重写（否则子类也是抽象类）|

```cpp

class Shape {
public:
    // non-virtual：所有形状的 ID 获取方式相同，不希望子类改变
    int getID() const { return m_id; }
    
    // virtual：希望子类重写，但父类提供默认实现
    virtual void draw() const {
        // 默认绘制逻辑
    }
    
    // pure virtual：子类必须实现自己的计算面积逻辑
    virtual double area() const = 0;
    
private:
    int m_id;
};
class Circle : public Shape {
public:
    // override draw（可选）
    void draw() const override {
        // 圆形特有的绘制逻辑
    }
    
    // 必须实现 area
    double area() const override {
        return 3.14159 * r * r;
    }
private:
    double r;
};
```
### 5.2 继承的主要价值

继承的主要价值**并非为了复用数据**，而是**与虚函数搭配使用，实现多态**。

> 📖 **参考**：cppreference 虚函数 —— “虚函数是特殊的成员函数，在派生类中被重写时，通过基类指针或引用调用时会调用派生类的函数。这是多态的基础。”“纯虚函数在基类中没有定义，派生类必须重写它，或者继续保持为抽象类。”

## 六、知识小结

### 6.1 三种关系对比总览

|对比项|复合（Composition）|委托（Delegation）|继承（Inheritance）|
|---|---|---|---|
|关系含义|has-a（有一个）|has-a（通过指针）|is-a（是一种）|
|UML 图示|实心菱形（黑色）|空心菱形（白色）|空心三角形|
|拥有方式|直接拥有**对象**|通过**指针**拥有|子类包含父类成分|
|生命周期|**同步**（同生共死）|**不同步**（可延迟创建）|**同步**（子类对象包含父类部分）|
|构造顺序|先内部后外部|先指针后指向对象|先父类后子类|
|析构顺序|先外部后内部|先指针后指向对象|先子类后父类|
|典型应用|Adapter 模式（如 queue）|pimpl 模式、引用计数|多态、虚函数|
|内存角度|外部对象包含内部对象|指针指向外部对象|子类对象包含父类数据|

### 6.2 核心概念速查表

|知识点|核心内容|关键要点|
|---|---|---|
|**复合（Composition）**|一个类内部包含另一个类的对象（has-a）|构造由内而外，析构由外而内；编译器自动调用内部默认构造函数|
|**Adapter 模式**|通过复合改造已有类的接口|如 `queue` 借用 `deque` 实现，功能不变，接口改名|
|**委托（Delegation）**|通过指针指向另一个类（composition by reference）|生命周期不同步；指针可指向不同实现|
|**pimpl（编译防火墙）**|Handle/Body 架构：对外接口不变，内部实现可切换|修改 Body 不影响 Handle，客户端无需重新编译|
|**引用计数**|多个对象共享同一份数据，通过计数管理|写时复制（Copy on Write）：修改时先复制再修改，不影响其他共享者|
|**继承（Inheritance）**|public 继承表示 is-a 关系|子类包含父类所有数据成员；构造/析构顺序与复合相同|
|**虚函数**|允许子类重写父类函数，实现多态|三种类型：non-virtual、virtual、pure virtual|
|**父类析构函数**|必须声明为 `virtual`|否则通过基类指针删除派生类对象会导致未定义行为|
